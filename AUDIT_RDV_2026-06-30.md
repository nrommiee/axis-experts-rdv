## 1. Résumé exécutif

**Axe 1 — « Bloqué X jours ».** La **seule** contrainte de délai minimum présente dans tout le
code est un **`minDate = aujourd'hui + 2 jours` codé en dur**, **GLOBAL** (non paramétrable par
organisation), et présent **uniquement dans la page PUBLIQUE `/prendre-rdv`**
(`src/app/prendre-rdv/page.tsx:249-255`). Le portail **authentifié** (`/demande`, celui qu'utilise
un client comme **CPAS de Bruxelles**) n'applique **aucun délai** : le calendrier autorise
« aujourd'hui » et la validation serveur n'exige que « date ≥ aujourd'hui » (max 90 j). **Il
n'existe aucun champ de délai/buffer par organisation** (ni dans `organizations`, ni dans
`portal_clients`, ni dans `custom_fields`). Conclusion : si des utilisateurs CPAS sont « bloqués
X jours », ce n'est **pas** dû à une config CPAS dans ce dépôt — voir les 3 hypothèses classées.

**Axe 2 — Flux agence.** Le flux est cohérent et le fix **PR #40** (`parent_id = false` sur
l'adresse de mission) est **correct et sans régression sur le bailleur** (le bailleur n'a jamais
eu l'agence comme `parent_id`). En revanche **3 risques réels** sont identifiés : (a) l'**identité
de l'agent individuel n'est pas tracée** dans Odoo si `resolveAgentAgency` échoue (repli sur le
partenaire partagé) ; (b) **risque d'invisibilité** des devis créés pendant ce repli pour le
contrôle d'ownership ; (c) **déduplication bailleur sensible à la casse** de l'email → doublons
`res.partner`.

## 2. AXE 1 — Bug « bloqué X jours » (délai de réservation)

### 2.1 Les deux parcours de prise de RDV (à ne pas confondre)

| Parcours | Page / route | Auth | Délai minimum appliqué |
|---|---|---|---|
| **Public** (sans login) | `src/app/prendre-rdv/page.tsx` → `POST /api/public/rdv` | non | **+2 jours codés en dur** (CODE) |
| **Portail authentifié** (clients : CPAS, agences…) | `src/app/demande/page.tsx` → `POST /api/submit-rdv` | oui | **aucun** (aujourd'hui autorisé) (CODE) |

CPAS de Bruxelles est un **client du portail** (`portal_clients.odoo_template_prefix = 'CPASBXL'`,
`odoo_partner_id = 77104`) — `supabase/migration.sql:84-85`, `supabase/migrations/organizations_data_migration.sql:38-49`.
Il passe donc par le **portail authentifié `/demande`**, qui n'applique aucun délai (voir 2.3).

### 2.2 La seule logique de délai du dépôt : +2 jours, GLOBALE, page publique

`src/app/prendre-rdv/page.tsx:249-255` :
```ts
// Date minimale : +2 jours
const minDate = useMemo(() => {
  const m = new Date();
  m.setDate(m.getDate() + 2);
  const pad = (n: number) => String(n).padStart(2, "0");
  return `${m.getFullYear()}-${pad(m.getMonth() + 1)}-${pad(m.getDate())}`;
}, []);
```
Appliquée comme attribut `min` sur les deux champs date : `src/app/prendre-rdv/page.tsx:1350` et
`:1359`. **Valeur exacte de X = 2 jours calendaires**, **codée en dur**, **identique pour tous les
clients du parcours public** (aucune lecture d'org). (CODE)

> Note : sur un `<input type="date">`, `min` empêche la sélection via le widget mais **ne bloque
> pas** une saisie clavier d'une date antérieure ; aucune revalidation du délai n'a lieu côté
> serveur public (voir 2.4). Le « blocage » ressenti est donc purement l'UI du datepicker.

### 2.3 Le portail authentifié n'a AUCUN délai (défaut = aujourd'hui)

- Composant calendrier : `src/components/ui/date-range-picker.tsx:79-82`
  ```ts
  const effectiveMin = React.useMemo(
    () => minDate ?? startOfTodayInZone(RDV_TIMEZONE),
    [minDate],
  );
  ```
  Le minimum effectif vaut `minDate` **si la prop est fournie**, sinon **aujourd'hui** (zone
  Europe/Brussels). Le matcher `{ before: effectiveMin }` désactive seulement les jours < ce min
  (`:143-151`).
- Usage réel dans `/demande` : `src/app/demande/page.tsx:1098-1114` — `<DateRangePicker>` est
  monté **sans prop `minDate`** → `effectiveMin = aujourd'hui`. **Aucun délai.** (CODE)

### 2.4 Validation serveur (portail) : « date ≥ aujourd'hui », max 90 j, pas de lead time

- `src/lib/validation/rdvDateSchema.ts:60-65` rejette uniquement `debutEpoch < todayEpoch`
  (« La date de début doit être aujourd'hui ou dans le futur »).
- Fenêtre max : `RDV_MAX_RANGE_DAYS = 90` (`:6`), contrôle `:73-79`.
- Appelée par `src/app/api/submit-rdv/route.ts:89-99`.
- **Aucun minimum de N jours** n'est présent. (CODE)
- Le serveur **public** (`src/app/api/public/rdv/route.ts`) ne valide **aucune** contrainte de
  date : `availability` est optionnelle dans le schéma (`src/lib/public-rdv/schema.ts:41-47`). (CODE)

### 2.5 Absence totale de paramètre de délai par organisation / type de prestation

- Table `organizations` — colonnes : `name, odoo_partner_id, odoo_agency_id,
  odoo_template_prefix, client_type, logo_url, product_config, contact_*, is_active`
  (`supabase/migrations/organizations.sql:8-23`). **Aucun champ délai/buffer/lead time.** (CONFIG/DB)
- Table `portal_clients` (`supabase/migration.sql:1-16` + ALTER `:49-82`). **Aucun champ délai.** (CONFIG/DB)
- `custom_fields` (per-org) : les champs définis sont des métadonnées de mission
  (`n_archi, etage, vivaqua, date_fin_tvx, motif_depart, date_els`…) — `supabase/migrations/0010_custom_fields.sql:110-126`
  et `0011_custom_fields_garage_dates.sql`. **Aucun champ ne pilote la fenêtre de réservation**
  (ce sont des valeurs écrites vers Odoo, pas des validateurs de date). (CONFIG/DB)

### 2.6 Sources « fantômes » de jours examinées

- **Fuseau / UTC** : `rdvDateSchema.ts` calcule « aujourd'hui » en `Europe/Brussels`
  (`:19-21`, `:55`) puis compare en epochs UTC dérivés du Y-M-D (`:23-26`). Le datepicker convertit
  ce Y-M-D Brussels en `Date` **locale** (`:44-59`). Pour des utilisateurs en Belgique, **pas de
  décalage** ; un décalage théorique n'apparaîtrait que pour un client à l'ouest de l'UTC. (CODE)
- **Week-ends / fériés** : aucun filtrage bloquant. Les week-ends sont seulement **stylés**
  (`date-range-picker.tsx:124-127`) et un **avertissement** non bloquant s'affiche pour
  week-end / urgence / < 48 h (`prendre-rdv/page.tsx:1365-1370`). Aucun jour férié géré. (CODE)
- **Double application d'un buffer** : non — un seul délai existe (+2 j public). Pas de second
  buffer client+serveur. (CODE)
- **Config CPAS « saine » vs « malade »** : impossible d'isoler un champ responsable car **aucun
  champ de délai n'existe** à comparer. CPASBXL ne diffère d'une org « saine » que par son
  `odoo_template_prefix` et ses templates Odoo (`src/lib/odoo.ts:91-100`), sans rapport avec les dates.

### 2.7 Cause racine et hypothèses classées

**Cause racine prouvée (parcours public) :** le délai « X jours » du parcours **public** vaut
**exactement 2 jours**, codé en dur dans `src/app/prendre-rdv/page.tsx:250-255`, **global**.

**Pour le cas CPAS (portail authentifié), le code n'impose aucun délai.** Le symptôme provient
donc d'une autre source. Hypothèses classées :

1. **(la plus probable) CPAS utilise/ a utilisé la page publique `/prendre-rdv`** (ou un lien la
   pointant), où X = 2 j s'applique à tous. **Test :** confirmer l'URL réellement diffusée aux
   agents CPAS. Si c'est `/prendre-rdv`, X = 2 j confirmé ; le correctif = rendre le `+2` configurable
   ou nul.
2. **Le « X jours » est un blocage côté Odoo / planning secrétariat**, hors de ce dépôt (le code
   ne fait que créer un `sale.order` en statut « En cours », `submit-rdv/route.ts:712`). **Test :**
   vérifier dans Odoo s'il existe une règle de disponibilité/calendrier ou un délai d'expert sur
   `x_studio_suivi_expert` / agenda. *(Non vérifiable sans runtime Odoo.)* ⚠️ HYPOTHÈSE À CONFIRMER.
3. **Mauvaise interprétation de la fenêtre max 90 j** ou de l'avertissement « < 48 h »
   (`prendre-rdv/page.tsx:1368`) comme un « blocage ». **Test :** demander à l'utilisateur la
   capture exacte du message vu et la date refusée ; recouper avec `rdvDateSchema.ts:60-79`.

### 3.5 Analyse PR #40 (`c1a17d5`) — `parent_id = false`

- Diff : **+14 lignes**, ajoute le bloc `submit-rdv/route.ts:915-920` (vérifié via `git show c1a17d5`).
- Historique : 1er commit reparentait l'adresse vers le bailleur (individu) → Odoo préfixait
  **quand même** (testé devis 29506) ; 2e commit pose `parent_id = false` (aucun parent → aucun préfixe).
- **Ce que ça corrige :** le `display_name` de l'adresse de mission n'est plus préfixé par le nom de
  la société agence.
- **Effets de bord :**
  - ✅ **Pas d'orphelinage du bailleur** : le bailleur n'a jamais eu l'agence en `parent_id` (P3) →
    PR #40 ne change rien pour lui.
  - ✅ **Mission/adresse intactes** : `partner_shipping_id` et `x_studio_adresse_de_mission` pointent
    toujours `adressePartnerId` (`:898-899`) ; `sale.order.partner_id` reste le bailleur (`:638,:666`).
  - ✅ **Non-agences non affectées** : le write `parent_id=false` est conditionné à `client_type==='agency'` (`:915`).
  - ⚠️ **Effet mineur (hygiène de données)** : l'adresse de mission devient un `res.partner`
    **autonome de niveau racine** (plus rattachée à l'agence dans l'arbre de contacts) → accumulation
    de contacts « adresse » orphelins dans Odoo. Cosmétique, non bloquant. (CODE)
